# AGENTS.md

## Project Overview

`scheduler` adalah Java 21/Spring Boot 4.1 service untuk menjadwalkan HTTP task, menjalankan task
group secara serial atau paralel termasuk nested group maksimum lima level, menyimpan execution
history, memublikasikan create audit ke Kafka, dan mengirim threshold/error alert ke
`centralized_alert`.

Stack utama:

- Java 21 dan virtual threads
- Spring Boot 4.1.0 dan Maven
- Spring MVC dan Jakarta Validation
- Spring Kafka untuk outbound audit event
- Spring JDBC, PostgreSQL, dan Flyway
- Java `HttpClient`
- `sdk-util` response, exception, security, OpenAPI, ECS logging, trace ID, dan MDC
- Actuator dan Prometheus
- JUnit 5, Mockito, dan Testcontainers

Prioritas desain:

- Durable schedule occurrence sebelum HTTP execution.
- Aman untuk multiple service instances melalui row locking dan execution lease.
- Bounded concurrency walaupun memakai virtual threads.
- At-least-once recovery dengan target API yang idempotent.
- Complete task history untuk monitoring.
- Tidak membocorkan task payload atau credential melalui log/API.

## Coding Guidelines

### Java Version

- Use records for immutable DTO/model values.
- Use `Instant`, `Duration`, `ZoneId`, and injected `Clock`.
- Use UTC for the JVM, JDBC session, persistence, logs, and API timestamps. A schedule `zoneId`
  may differ only because cron interpretation is an explicit business-scheduling boundary.
- Use the configured `schedulerVirtualThreadExecutor`; never create executors in business methods.
- Preserve interruption whenever catching `InterruptedException`.
- Keep virtual-thread concurrency bounded through the shared semaphore.
- Avoid raw types, legacy date APIs, and mutable shared state.

---

## Naming Convention

- Classes/records/enums: `PascalCase`.
- Methods/variables: `camelCase`.
- Constants: `UPPER_SNAKE_CASE`.
- Packages: lowercase under `com.mac.scheduler`.
- REST DTOs: `Request`/`Response` suffix.
- Configuration bindings: `Properties` suffix.
- Business exceptions: `Exception` suffix.
- Scheduler-specific ECS fields belong in `SchedulerLogFields`.

---

## Spring Guidelines

- Controllers validate, call services, return SDK `ResponseDTO` helpers, and place
  `@PreAuthorize` with `PERM_<resource>:<action>` on protected endpoint methods.
- Service implementations must not carry HTTP endpoint authorization annotations.
- Services own task/group/schedule policy and execution orchestration.
- Repositories own SQL and result mapping.
- The polling job is a boundary; it must delegate claim and execution logic.
- Use constructor injection, never field injection.
- Bind settings under `scheduler.*`; keep secrets externalized.
- Organize every application YAML by major property group and precede each group with the
  three-line banner used in this repository (`# =========================`, an uppercase section
  name, and the same separator). Separate sections with one blank line and never change property
  hierarchy merely for formatting.
- Do not duplicate `sdk-util` response, global exception, security, logging, or OpenAPI setup.
- Keep the engine conditional on `scheduler.engine.enabled`.
- Never hold the claim transaction open during HTTP execution.

---

## Entity Rules

Models are JDBC/domain records, not JPA entities.

- Never return internal models directly from REST APIs.
- Keep stored enum names stable.
- Keep task headers/request body out of monitoring responses.
- Store duration/threshold consistently in milliseconds.
- Use UUIDs generated by the application.
- Treat task, group, schedule, execution, and task history as separate lifecycle concepts.

---

## Mapper

Mapping is currently explicit because creation includes normalization/defaulting. Do not add
MapStruct without an intentional project-wide decision.

- Normalize names, headers, URI, durations, and target fields before persistence.
- Keep history response mapping in the history service.
- Do not include credentials or raw request bodies in response mapping.

---

## Database

- Use `NamedParameterJdbcTemplate` and parameterized SQL.
- Every schema change requires a new Flyway migration; never edit an applied migration.
- Preserve `FOR UPDATE SKIP LOCKED` for multi-instance claims.
- Insert a unique schedule occurrence before advancing `next_execution_at`.
- Keep `(schedule_id, scheduled_for)` unique.
- Keep `(execution_id, task_id)` unique for task history.
- Preserve nested-group relations in `scheduler_group_group` and the five-level depth limit.
- Claim/lease operations must be short transactions.
- HTTP calls must run outside transactions.
- Verify one-row state transitions where exactly one update is expected.
- Index history filters and due/lease queries.
- Never enable Hibernate auto-DDL.

---

## Error Handling

- REST errors use `sdk-util` `GlobalExceptionHandler`.
- Use `ResourceNotFoundException` for 404.
- Use `SchedulerConflictException` for duplicate names/resources.
- Treat `IllegalArgumentException` as 400 only for invalid client input.
- Catch broad exceptions only at polling, virtual-thread, HTTP-client, or alert-client boundaries.
- Persist a safe English error summary; keep detailed stack traces only in structured internal logs.
- Threshold alert failure must not overwrite the original task result.
- Publish successful task, group, and schedule creation to the audit Kafka topic. Kafka publish
  failure must be logged and reported through a sanitized centralized error alert.
- Report terminal HTTP 5xx, scheduler/virtual-thread, and task-execution failures to
  `centralized_alert`; alert delivery remains best effort and must not replace the original result.
- Never silently swallow Future, scheduler, or execution-state failures.

---

## Logging

- Use `StructuredLog`, `LogFields`, and `SchedulerLogFields`.
- Include schedule ID, execution ID, task/group ID, duration, threshold, and HTTP status when known.
- Use execution ID as `trace.id` for schedule work.
- Copy MDC before parallel task submission and use `StructuredLog.withMdc` in the child thread.
- Always pass caught exceptions to internal error logs.
- Never log task bodies, authorization headers, JWTs, target response bodies, or alert credentials.
- Do not use `System.out` or concatenated business logs.

---

## Validation

- Use Jakarta Validation for request syntax and sizes.
- Validate positive durations, supported schemes, host allowlist, cron expressions, and timezone in
  the service layer.
- A TASK schedule accepts only `taskId`; a GROUP schedule accepts only `groupId`.
- Reject duplicate/unknown task IDs in a group.
- Reject duplicate/unknown child groups, circular/shared group branches, repeated tasks across a
  hierarchy, and nesting deeper than five group levels.
- Reject date combined with from/to history filters.
- Keep client-facing messages in English.

## Testing

Every behavior change needs focused tests.

### Unit Test Coverage Standard

- Unit-test line coverage must be at least 90% for production business code.
- New or changed business logic must maintain at least 90% line coverage before a task is
  considered complete.
- Measure coverage with JaCoCo when reporting or enforcing the percentage; never estimate coverage
  from the number of tests.
- Coverage scope must include controllers, services, repositories, jobs, exception handlers, and
  business utilities. Pure DTOs, enums, generated code, and trivial Spring bootstrap/configuration
  classes may be excluded when the exclusion is explicit and justified.
- Do not add meaningless assertions, invoke code without verifying outcomes, or weaken exclusions
  merely to reach the target. Cover success, validation, failure, retry/recovery, concurrency, and
  boundary behavior according to the risk of the changed code.
- If the 90% target cannot be verified because JaCoCo is not configured or a required external
  dependency is unavailable, report that limitation explicitly; do not claim the target passed.

- Unit-test cron and timezone calculation.
- Test task endpoint/header/duration validation.
- Test serial order and real parallel behavior.
- Test nested group execution, owning group history IDs, cycles, duplicates, and depth limits.
- Test claim materialization, stale lease recovery, and completion transitions.
- Test history date/range/group/task/threshold filters.
- Test non-2xx, timeout, interruption, and threshold alert behavior.
- Use Testcontainers PostgreSQL for Flyway and repository SQL.
- Avoid external HTTP, identity provider, or alert dependencies in unit tests.
- Use fixed `Clock` values.

## API Design

Current contracts:

- `POST /api/v1/tasks`
- `POST /api/v1/task-groups`
- `POST /api/v1/schedules`
- `GET /api/v1/histories`

- Return `ResponseDTO`/`ResponsePagingHelper` from `sdk-util`.
- Return 201 for creation and 200 for history.
- Keep JSON fields and enum values backward-compatible.
- Keep history bounded with limit/offset and maximum page size.
- Do not expose stored task secrets through management/monitoring endpoints.

---

## Performance

- Preserve global semaphore limits.
- Do not replace virtual threads with an unbounded platform-thread pool.
- Keep claim batch bounded.
- Do not wait on HTTP while holding database locks.
- Do not fetch response bodies when task execution only needs status.
- Keep history query predicates index-friendly and time-bounded.
- Set execution lease longer than valid maximum group runtime.
- Measure before changing pool, claim, poll, or parallelism defaults.

---

## Security

- Never commit production DB credentials, OAuth tokens, task authorization headers, or real data.
- Require HTTP/HTTPS and reject embedded URI credentials.
- Use `scheduler.http.allowed-hosts` in production to reduce SSRF risk.
- Do not allow tasks to override `Host`, `Content-Length`, or `X-Correlation-Id`.
- Target services must still authenticate and authorize scheduler requests.
- Do not declare or override `sdk.security.permit-all-paths` in this service. The canonical public
  path policy is owned by `sdk_util`; CORS remains an explicit service configuration.
- Keep task request bodies and headers out of logs/history responses.
- Treat changes to stored headers or outbound authentication as security-sensitive.

## Before Finishing Any Task

1. Inspect `git status` and preserve user changes, including `context.txt`.
2. Compile and run the smallest relevant tests while developing.
3. Run `mvn test` for code changes.
4. Run `mvn clean verify` for cross-layer/database/execution changes.
5. Run `git diff --check`.
6. Confirm no HTTP call occurs inside a transaction.
7. Check multi-instance claim and crash-recovery semantics.
8. Remove unused imports and temporary/generated files.
9. Update README, `.env.example`, and Flyway migrations when behavior/configuration changes.
10. Report external dependencies or permissions that block validation.

## Pull Request Checklist

- Tests pass; Testcontainers status is reported.
- Schema changes use a new migration.
- Schedule occurrences are durable and uniquely claimed.
- Serial/parallel and threshold behavior are tested.
- History filters remain bounded and indexed.
- Trace/MDC survives asynchronous boundaries.
- Structured logs and API responses contain no secrets.
- Configuration defaults and examples are updated.
- No `target/`, `.env`, generated artifacts, or credentials are committed.

## Things Never To Do

- Do not execute HTTP inside the schedule claim transaction.
- Do not remove unique occurrence/history constraints.
- Do not replace `FOR UPDATE SKIP LOCKED` with an in-memory-only lock.
- Do not create an executor per schedule or task.
- Do not silently drop failed or stale executions.
- Do not lose interruption or MDC across virtual threads.
- Do not log or expose task headers/body/secrets.
- Do not broaden host allowlists, public paths, or CORS casually.
- Do not edit applied Flyway migrations.
- Do not use destructive Git/database commands without explicit authorization and verified targets.

## Preferred Code Style

Prefer small cohesive methods, constructor injection, immutable records, parameterized SQL,
explicit boundary handling, composition over inheritance, and readable code over clever code.
Match surrounding formatting and avoid unrelated mechanical rewrites.
